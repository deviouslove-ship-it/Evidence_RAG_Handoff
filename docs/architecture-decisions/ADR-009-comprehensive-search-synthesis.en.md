# ADR-009 — Four-channel comprehensive search, content groups, and checked synthesis (G2, G4, G5)

- Date: 2026-11-07
- Status: Implemented
- Basis (căn cứ): the finalized design `docs/thiet-ke-tra-cuu-hieu-luc.md`, sections 6, 7, 8, and 12; decisions D3, D4, D6, D8, D9, D11, D13, and D15; consistency points 5, 6, 9, 10, 12, and 13.

## 1. Comprehensive search (G2)

1. **Local embedding through the Model Registry.** The `embedding` stage uses an OpenAI-compatible adapter (`POST /embeddings`); the trial used a standalone Ollama and `qwen3-embedding:0.6b` (1,024 dimensions). The endpoint, the model, and the install path live only in the Registry and in environment variables; the code does not know the model name. The `embedding` and `rerank` stages are **never** sent to a `public` profile, in either mode (`LOCAL_ONLY_STAGES`).
2. **A vector index sized to the model** (migration `0012`): the `node_embeddings.embedding` column does not fix the number of dimensions; each `embedding_indices` row records the model, the version, the number of dimensions, and its own HNSW index `((embedding::vector(D)) vector_cosine_ops) WHERE embedding_index_id = …`. Changing the model means opening a new index version with `scripts/build_embeddings.py --rebuild`; the old index keeps serving until the new index is complete (the G5 tool). The text sent for embedding is the document number + the citation label + the clause text, at most 800 characters (a machine without a GPU).
3. **Four channels fused with RRF** (k = 60): exact (Search v1 SQL, counted in full up to the cap of 8,000), semantic (N = `EVIDENCE_SEMANTIC_TOP_N`, relative threshold `EVIDENCE_SEMANTIC_RELATIVE_THRESHOLD` against the nearest clause (Khoản)), concept expansion (approved `concept_terms`; when there are fewer than `EVIDENCE_CONCEPT_MIN_TERMS`, the `expand` stage suggests terms, which are shown so the user can deselect them and are saved as a proposal waiting for approval), and administrative-document (văn bản) relations (clauses of an administrative document that has an approved relation, or a consolidation (hợp nhất) or guidance relation, with the top 20 administrative documents). **Stable tie-break (2026-11-08):** the RRF formula (k = 60) and the channels are unchanged; when two clauses tie (in the exact channel, the same tier and the same score; in the relation channel, the same rank; and in the RRF fusion, the same score and the same best rank), order is fixed by the administrative-document number, the SHA-256 hash of the file (this separates administrative documents that share a document number), then the clause position inside the administrative document (the ordinal prefix of `document_nodes.path`, that is Article (Điều) → Clause (Khoản) → Point (Điểm) order). Previously the clause UUID was used, and that was random on each import. Comparison is by bytes (`COLLATE "C"`), and does not depend on the server locale. The UUID remains only as the last resort.
4. **A result set fixed for the turn** (`ResultSetStore`): RAM only, at most 20 sets per person, expiring after `EVIDENCE_RESULT_SET_TTL_SECONDS`; only the owner of the set can read it; every page re-checks permission and provenance.
5. **Batched rerank** (stage `rerank`, a local model) has been **optional and off by default** since 2026-11-07 (`EVIDENCE_RERANK_DEFAULT=false`; a request may send `rerank: true`): the first `EVIDENCE_RERANK_TOP_N` candidates, in batches of `EVIDENCE_RERANK_BATCH_SIZE`; the rest keep RRF order; no candidate is dropped; the response includes `ranking`. The practical default of “Tìm toàn diện” (“Comprehensive search”) is pure RRF.
6. **An honest scope:** the categories, the number of administrative documents in scope, the data date, the semantic-channel cap and threshold, the number of clauses that have no vector, and the number of clauses found only through the semantic or relation channel; when the set is empty: “Chưa thấy trong kho …” (“Nothing found in the corpus …”), and never “đã tìm hết” (“the search is exhaustive”).
7. **D9:** three groups by default, “Còn hiệu lực (đã xác minh)” (“In effect (verified)”), “Chưa xác minh hiệu lực” (“Effectivity (hiệu lực) not verified”), and “Hết hiệu lực, bị thay thế, tạm ngưng” (“No longer in effect, replaced (thay thế), suspended”) (collapsed, and still counted); “Tìm toàn bộ” (“Search everything”), “Đối chiếu lịch sử” (“Compare against history”), or a lookup date other than today → a single list. Status and verification filters run over the whole set.
8. **Administrative-document groups (D3)** are computed at query time: a partially amended (sửa đổi) or consolidated administrative document belongs to the group of the original administrative document; a replaced administrative document belongs to the group of the replacing administrative document; an original outside the granted permissions is recorded only as “có văn bản liên quan ngoài phạm vi được cấp quyền” (“there is a related administrative document outside the granted scope”).

## 2. Content groups and synthesis (G4)

1. `content_taxonomy`, `labeling_rules`, `node_labels`, and `node_label_runs` (migration `0013`); 11 initial groups were proposed by the implementation (the design does not list the names) and can be edited or added in the database. A phrase rule assigns a label immediately (`auto`); the `label` stage proposes a label for a clause (Khoản) that has none (`proposed`), assigned lazily at synthesis time, under the `ai_label_budget` cap; a `REVIEWER` with `can_review` approves in a batch.
2. Synthesis (`POST /api/v1/synthesis`) runs on the result set: group by content group when there is a label, otherwise by administrative document (văn bản); a batch is ≤ `max_evidence_per_batch`, and each turn is ≤ `token_budget` and `max_batches_per_run` (an administrator configures this at `/api/v1/admin/synthesis-settings`, stored in `security_policies`); the report is “Đã tổng hợp N trong M căn cứ, K nhóm còn lại” (“Synthesized N of M evidence (căn cứ) items, K groups remaining”); the buttons are “Tổng hợp tiếp” (Continue synthesis) and “Mở rộng phạm vi” (Expand the scope) (this doubles the cap).
3. Checks in code (`synthesis/checks.py`): the evidence code belongs to the set that was issued; a number, a date, a document number, and an Article (Điều)/Clause (Khoản)/Point (Điểm) must occur in the attached evidence (the portion sent to the model); a business-conclusion word outside quotation marks → drop the point; a missing fact → “chưa kiểm chứng” (“not yet checked”).
4. Hybrid Auto for `summarize`: escalate to the API when no local point passes the checks, or when the user asks for “Phân tích sâu” (Deep analysis); if there is no evidence (căn cứ), do not call a model.

## 3. Quality (G5)

- `evaluation/coverage/topics.json` (8 topics, 24 ways of asking) and `run_coverage.py` measure the rate at which required evidence (căn cứ) is found, with every channel and with each channel alone, reading the whole result set through pagination.
- `evaluation/coverage/measure_g3_relations.py` measures precision and coverage of relations at Article (Điều)/Clause (Khoản) level.
- **A dedicated reranker (cross-encoder) is new and still experimental.** The default is still a local LLM in batches (`EVIDENCE_RERANK_BACKEND=llm`). A trial integrated Qwen3-Reranker-0.6B on CPU through a local service (`scripts/local_reranker_server.py`, `EVIDENCE_RERANK_BACKEND=cross_encoder`, loopback address only) and measured it on 100 administrative documents (văn bản): no option beat pure RRF by a statistically meaningful margin, and both rerankers took 32 to 48 seconds per question on CPU. The default has not been changed; see `docs/evidence/2026-11-07-g5-rerank/REPORT.md`. The two evidence items G5 did not find are a candidate-retrieval failure (the semantic-channel threshold), not a ranking failure.
